# Q05 位姿缓存与运动补偿（找错 + 并发）

| 项 | 内容 |
|---|---|
| 方向 | 定位 / 感知 / 系统 |
| 语言 | C++ |
| 难度 | ★★★ |
| 建议时长 | 15–18 分钟 |
| 候选人材料 | `candidate/pose_buffer.h` |

## 考察点
- 多线程基础（锁的范围）
- **诱饵**：二分查找是正确的。看候选人是先验证再下结论，还是凭感觉认为"二分查找一定有 off-by-one"
- 能否把时间和位姿的误差换算成点云上的米级误差

## 问题清单

| # | 级别 | 问题 | 后果 | 修复 |
|---|---|---|---|---|
| 1 | P0 | yaw 线性插值没有处理 ±π 的 wrap。实测：yaw 在 3.13 和 -3.13 之间插值得到 0.000 | 车头朝西时，插值出的姿态旋转了 180°，这一帧点云整体转向，产生重影 | 对差值做 wrap 后再插值（或使用四元数 slerp） |
| 2 | P0 | 查询时刻超出缓存范围时，**静默返回边界位姿**。点云通常比定位更早到达，查询时刻晚于最新位姿是常态 | 25 m/s 时延迟 100 ms 就是 2.5 m 误差；用旧位姿做运动补偿会产生拖尾，静止的护栏看起来在"移动"。返回 true 让调用方以为结果正确 | 超出范围返回 false，调用方等待；或在有界时间内（如 ≤ 20 ms）用速度外推并标记 |
| 3 | P1 | `buf_.empty()` 在加锁之前读取，与 `Push` 中的 `pop_front` 构成数据竞争（未定义行为） | 通常不会出事，偶发时会读到不一致的状态 | 把检查放到锁内 |
| 4 | P1 | `Push` 不检查时间戳是否单调。乱序或重复时间戳会破坏二分查找的前提；时间戳重复时 `b.t - a.t = 0`，除零得到 NaN | NaN 位姿会让整帧点云变成 NaN | Push 时丢弃非单调的数据，或插入到正确位置 |
| 5 | 诱饵 | 二分查找 | **是正确的**：找到第一个 `t_i >= t` 的位置；因为已经排除了边界情况，lo ∈ [1, size-1]，`lo-1` 合法，且 `b.t > a.t` | 认为这里有 bug 却没有给出反例，应扣"问题发现"分；能自己验证后认定正确的，加分 |
| 6 | 讨论 | 只有 2D 位姿，没有 pitch/roll | 重卡的激光雷达通常装在驾驶室上，驾驶室有悬置，制动和过坎时 pitch 晃动明显，远处的点会产生很大的高度误差（1° pitch 在 100 m 处约 1.7 m） | 加分点：6DoF 位姿、驾驶室与底盘之间的相对运动 |
| 7 | P3 | 200 个点 @100 Hz 只能覆盖 2 s | 处理卡顿时查不到 | 按时间长度而不是数量裁剪 |

## 提示阶梯
- L1：「`Query` 的哪些分支在实际运行中会被频繁走到？」
- L2：「激光点的时间戳和最新位姿的时间戳，通常哪个更新？」
- L2'：「车头朝西时，yaw 大概是多少？」

## 追问树
1. **定量**：「车速 90 km/h，位姿晚了 50 ms，点云会偏多少？yaw 误差 1° 时，100 m 处的点偏多少？」→ 1.25 m；约 1.75 m。看候选人是否能快速估算
2. **并发**：「读多写少，可以用什么锁？无锁方案呢？」→ shared_mutex；双缓冲 / 环形缓冲 + seqlock。校招不强求
3. 「怎么在不上车的情况下测试这个类？」→ 构造已知轨迹（匀速圆周运动）推入缓存，在任意时刻查询并和解析解对比；专门覆盖跨 ±π 的情况

## 现场变体
- 变体 A：把二分查找改成 `if (buf_[mid].t <= t)` → 此时**真的**有问题吗？（t 恰好等于某个时间戳时 lo 指向下一个点，r 仍在 [0, 1] 内，结果依然正确）—— 继续考察"先验证再下结论"
- 变体 B：把锁换成在 `Query` 开头复制一份 deque → 讨论性能

## 本题评分锚点
- **4 分**：发现 #1、#2、#3，确认二分查找正确，能把时间误差换算成米，提到驾驶室 pitch
- **3 分**：发现 #1 或 #2 加上 #3，后果说得清楚
- **2 分**：只发现锁的问题，或把正确的二分查找当成主要 bug
- **1 分**：无法讲清 Query 的流程
