# Q07 坐标变换（找错 + 测试设计）

| 项 | 内容 |
|---|---|
| 方向 | 通用（所有方向都会用到） |
| 语言 | Python / NumPy |
| 难度 | ★★ |
| 建议时长 | 12–15 分钟 |
| 候选人材料 | `candidate/transforms.py` |

## 考察点
坐标变换是新人最常写错、也最难排查的一类 bug。这道题有一个很好的设计：**3 个 bug 同时存在，但"来回转一圈"的测试依然能通过**（已实测）。所以除了找 bug，更重要的是考察候选人怎么设计测试。

## 问题清单

| # | 级别 | 函数 | 问题 | 修复 |
|---|---|---|---|---|
| 1 | P0 | `inv_T` | 平移部分应为 `-Rᵀ t`，而不是 `-t`。只有 R = I 时才正确 | `Ti[:3, 3] = -R.T @ t` |
| 2 | P0 | `transform_points` | 点是行向量，`homo @ T` 相当于 `Tᵀ p`。应为 `homo @ T.T`。实测：纯平移时平移量被直接丢掉，旋转方向也反了 | `(T @ homo.T).T` 或 `homo @ T.T` |
| 3 | P0 | `lidar_to_world` | 组合顺序错误。根据约定，下标应该"首尾相消"：`T_world_lidar = T_world_vehicle @ T_vehicle_lidar` | 交换顺序 |
| 4 | 诱饵 | `world_to_lidar` | 组合顺序是**正确的**：`inv(T_world_vehicle @ T_vehicle_lidar) = T_lidar_world` | 指出它是正确的，并说明理由，加分 |
| 5 | 诱饵 | `make_T` | 正确 | — |

## 测试设计（本题的核心追问）
- 「lidar→world→lidar 来回一圈等于原值」**测不出来**：实测在 3 个 bug 同时存在时，来回一圈仍然返回原值（错误是互相抵消的）。这是本题最重要的知识点：**对称的测试抓不住对称的错误**
- 有效的测试：
  1. **已知答案测试**：绕 z 轴旋转 90° 加平移 (1, 2, 0)，点 (1, 0, 0) 应该变成 (1, 3, 0)
  2. `inv_T(T) @ T == I`，并且 `inv_T(T)` 与 `np.linalg.inv(T)` 一致（能抓到 #1）
  3. 与另一套独立实现对比（如 scipy 的 Rotation）
  4. 物理检查：把点云转到世界系，地面点的 z 应该接近地面高程；静止物体在多帧之间应该重合

## 提示阶梯
- L1：「用"下标相消"的规则检查一下每个组合。」
- L2：「取一个具体的旋转（90°）和一个点，手算一下 `transform_points` 的结果。」

## 追问树
1. 「为什么这类 bug 很难被发现？」→ 很多实际场景中外参的旋转接近单位阵，或者车辆朝向接近 0，错误被掩盖；只在某些朝向下才会暴露
2. **重卡加分**：「如果激光雷达装在挂车上，`T_vehicle_lidar` 还是常量吗？」→ 不是，它依赖铰接角，需要实时估计铰接角
3. 「驾驶室上的雷达呢？」→ 驾驶室相对底盘有悬置运动，严格来说外参也是时变的
4. 「点云很大（N = 200k），这个实现有什么性能问题？」→ hstack 每次都会分配内存；可以直接用 `pts @ R.T + t`

## 现场变体
- 变体 A：修好 #1、#3，把 `world_to_lidar` 改成 `inv_T(T_vehicle_lidar) @ inv_T(T_world_vehicle)` → 这是对的吗？（**是对的**：(AB)⁻¹ = B⁻¹A⁻¹。再把顺序对调问一次，对调后就是错的）
- 变体 B：改用四元数 (w, x, y, z) 与 (x, y, z, w) 顺序混用

- **3 分**：找到 3 个 bug 中的 2 个，测试设计合理
