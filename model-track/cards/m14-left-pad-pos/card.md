# M14 左 padding 的位置编号 · `推理` `KV cache` `LLM/VLM 部署`

**入口（照念）**：「batch 生成时用了左 padding，position_ids 这样写有问题吗？」　**时长** 6–8 分钟
（**判断型**：答案取决于位置编码，不预设一定有 bug；补全了旧题库 R09 缺少的代码）

| 级别 | 要点 | 说明 |
|---|---|---|
| 核心 | 先问"用的是什么位置编码" | pad 占用了位置编号：左 padding 的样本，有效 token 从位置 2 开始，单独推理时从 0 开始（实测见验证脚本） |
| 诱饵 | 纯 RoPE 下基本等价 | RoPE 的注意力分数只依赖相对位置。所有有效 token 整体平移，分数不变（实测 `allclose = True`），pad 又被 mask 掉，所以结果只有数值误差。**直接断言"输出会不一样"是不精确的** |
| P0 | 可学习的绝对位置编码 | 平移后取到的是不同的 embedding（实测不相等），batch 推理和单条推理结果不一致 |
| P1 | 依赖绝对位置或长度的变体 | 动态 NTK 等随长度变化的 RoPE 缩放、超过训练长度的位置、多模态的 M-RoPE（视觉 token 的位置是 2D/3D 的）→ 平移不再"无害" |
| P1 | 跨请求复用前缀 KV cache | 同一前缀在不同 batch 里位置编号不同，缓存的 K 已经带了旋转，不能直接复用（关联旧题库 D04） |
| 推荐写法 | — | `pos = (attn.cumsum(-1) - 1).clamp(min=0)`；之后每步 `next_pos = pos.max(-1, keepdim=True).values + 1`，attention mask 每步拼接 1 |

**追问 · 预研**：从公式推一下为什么 RoPE 是平移不变的？哪些长上下文扩展方法会破坏这一点？
**追问 · 落地**：你会写什么测试证明 batch 推理和单条推理一致（逐步比较 logits，设定容差）？continuous batching 时位置怎么管理？

**锚点**：4 = 先问位置编码，能推出 RoPE 平移不变，并指出何时不再成立；3 = 给出 cumsum 的写法和一致性测试；2 = 只说"pad 不该占位置"，讲不出后果；1 = 不理解 position_ids
